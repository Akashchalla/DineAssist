# DineAssist — restaurant table monitor (Phases 1–4)

**[Open the public evaluation demo](https://dineassist-six.vercel.app)** — A browser-only version is available in `web/`, with Vercel configuration at the repository root. See [website setup and deployment](web/README.md). It includes an interactive sample floor plan and the saved detector video; it does not connect to a live camera.

DineAssist watches a dining-room camera (or a recorded video), estimates whether
each table is **free**, **occupied** or **needs cleaning**, times how long guests
have waited for a greeting, and shows it all on a host-stand dashboard.

| Phase | What it adds | Main files |
| --- | --- | --- |
| 1 | Draw table outlines on a still camera image | `scripts/map_tables.py` |
| 2 | Detect and track people, match them to tables | `scripts/detect_people.py` |
| 3 | Table states, timers, alerts, SQLite history, JSON API | `backend/`, `scripts/state_client.py` |
| 4 | Streamlit dashboard for the host stand | `dashboard/`, `.streamlit/config.toml` |

## Phase 1: map your tables

Think of this step as drawing a restaurant floor plan on top of a camera photo.
The program takes one picture from a video or camera, lets you click around each
table's seating area, and remembers those outlines. The technical name for an
outline made from connected points is a **polygon**. A rectangle is a four-point polygon.

Put your video at `data/videos/restaurant.mp4`, or replace the path below with
your real filename. Then run:

```bash
python scripts/map_tables.py --source data/videos/restaurant.mp4
```

A desktop window shows the first video image. It stays frozen so the picture
doesn't change underneath your clicks. The video connection closes after that
image is read; Phase 2 will add continuous processing.

To use an image from approximately 10 seconds into a saved video:

```bash
python scripts/map_tables.py --source data/videos/restaurant.mp4 --seconds 10
```

Seeking precision depends on the video format. `--seconds` does not apply to live streams.

## Draw your tables

Click around the outside of a table's **seating area, including the chairs**, in
clockwise or counterclockwise order. Avoid overlapping neighboring table zones
or including busy walkways. Use at least three corners; four works for a rectangle.
You do not need to click the first corner a second time.

Outlines drawn around only the tabletop tend to miss diners: a seated person's
box is mostly over the chair, so too little of it overlaps the zone. If a table
with visible guests stays green in the Phase 2 preview, redraw it to include
the chairs (see `--overwrite` below).

With the drawing window focused, use these lowercase keys:

| Action | Control |
| --- | --- |
| Add a corner | Left mouse click |
| Finish this table | `n` |
| Undo the last corner | `u` |
| Clear the unfinished outline | `c` |
| Delete the last completed table | `d` |
| Save all completed tables and exit | `s` |
| Quit without saving | `q` or Escape; press twice if there is unsaved work |

Finish each table with `n`; the program assigns `table_1`, `table_2`, and so on.
Repeat for other tables, then press `s`. The terminal prints the saved file's path.
The blue outlines are drawing guides; occupancy colors arrive in later phases.
Closing the window with its close button discards unsaved work.

Saving refuses an unfinished outline: press `n` to finish it or `c` to remove it.
Existing files are protected. To intentionally redraw and replace a map, add
`--overwrite`. This starts a new drawing; it does not load existing polygons.
For a separate camera, use its own `--camera-id` and `--output` file.

## Use an RTSP camera instead

RTSP is a way for a security camera to send live video over a network. Obtain the
actual stream address from your camera's configuration. This address is only a template:


The computer must be able to reach the camera. The program uses the current image
and tries to limit connection and read waits to 10 seconds each through FFmpeg.
Support depends on the installed OpenCV backend and the camera's video format.

To keep a real camera password out of your typed shell history, you can instead use

```bash

unset CAMERA_SOURCE
```

The JSON does not store the source URL or password. OpenCV's own connection-error
messages can contain connection details; check those before sharing logs.

## What the saved coordinates mean

JSON is a text format for storing structured information. Each polygon contains
`[x, y]` pairs: `x` measures pixels from the image's left edge, and `y` measures
pixels from its top edge. A **pixel** is one tiny dot in an image.

The mapper saves coordinates for the original video image, even when the preview
is smaller. `frame_size` records the original width and height so Phase 2 can
check that its incoming images match. The UTC timestamp records when the map was
saved. `schema_version` identifies the file format for future code.

Keep the camera fixed. If its view, crop, or rotation changes, redraw the zones.
Changing resolution requires matching coordinate scaling in the detection code.
No video or still image is saved by this script.

## If something goes wrong

| Message or symptom | Meaning and fix |
| --- | --- |
| `No module named cv2` or `numpy` | This Python environment lacks the packages. Activate `.venv` and run `python -m pip install -r requirements.txt` there. Use `python -m pip` so installation targets the same Python you run. |
| `Video file not found` | The filename or current folder differs from the command. Run the `cd` command above and check the filename, or use the video's full path. |
| `Could not open the video` | The file cannot be decoded, or the camera connection failed. Check that the video plays locally; for RTSP, check the URL, credentials, network, and camera settings. |
| `No image received` | The chosen time may be past the end, or the feed stopped. Try without `--seconds` or check the camera stream. |
| No drawing window / GUI error | This needs a local desktop session and regular `opencv-python`. A headless package or remote notebook cannot provide this window. Use the project virtual environment from a local terminal. |
| `Edges cross` | The clicked corners make a tangled outline. Clear it with `c`, then click in order around the outside. |
| `Output already exists` | A map is already saved. Choose another `--output` filename, or deliberately use `--overwrite` to replace it. |

## Architecture

```text
Video / RTSP camera
       |
       +-- Phase 1: frozen frame -> manual polygons -> JSON map
       |
       +-- Phase 2: continuous frames + map -> YOLO26 person detection / tracking
                       |
                  Phase 3: per-table state and timers -> SQLite event history
                       |                              -> console alerts
                    FastAPI JSON API
                       |
                  Phase 4: Streamlit dashboard
```

Keep the video processing worker separate from API requests: refreshing a
dashboard should not start another detector. SQLite is built into Python;
every other package for all four phases is listed in `requirements.txt`.

Before building the states, we will define how long a person must stay before
counting as seated, and how to handle temporary missed detections. A generic
person detector cannot reliably distinguish staff from customers. Uniform color
can be a hint but requires testing against your actual camera view. Someone
entering a zone also does not prove that a table was cleaned. We'll use explicit
assumptions and a staff confirmation option when needed. Likewise, time seated
can be displayed, but it does not establish when a party will leave.

Phase 1 creates the map. You learn how camera positions become stored coordinates.
The next step after saving a real map is Phase 2: detecting people in those zones.

## Phase 2: watch people in your mapped zones

The new code is already saved in `scripts/detect_people.py`. It reads your video
one image at a time, asks YOLO to find people, and compares their boxes with your
table outlines. We need this step to turn pictures into observations that the
state machine can use in Phase 3. Your saved table map is only read, never edited.

The detector uses the small pretrained **YOLO26** nano model (`yolo26n.pt`), released by Ultralytics on January 14, 2026 (Ultralytics 8.4.0). YOLO26 is built for edge devices and removes the separate duplicate-box filtering step (NMS), which made it about 15% faster than YOLO11 in our CPU test on the sample video. The previous `yolo11n.pt` still works with `--model models/yolo11n.pt`. **Pretrained** means it
has already learned to recognize common objects; we request only the person
category. Its learned parameters, called **weights**, download on first use into
`models/`. ByteTrack links detections across images and assigns temporary numbers
such as `P7`. This is **tracking**, not identifying a person's real identity.

### Run it

After opening a terminal in this project and activating `.venv`, install the
updated packages if you have not already done so:

```bash
python -m pip install -r requirements.txt
```

Then run the detector:

```bash

```

It uses `data/videos/restaurant.mp4` and `data/zones/tables.json` by default.

| What you see | Meaning in Phase 2 |
| --- | --- |
| Cyan rectangle, such as `P7 86%` | A detected person, their temporary tracking ID, and model confidence |
| Red table outline, such as `T2: 3` | Three people were matched to table 2 in this image |
| Green table outline | No person was matched in this image; this does **not** confirm the table is free or clean |

Press **Space** to pause/resume and **q** or Escape to quit. When the video ends,
the final image remains open for inspection until you quit. `P?` means a detection
currently has no tracker ID. IDs can change after occlusion or missed detection.
Confidence is the model's score, not a guarantee of correctness.

### How matching works

Imagine a person's rectangle covers 100 squares of graph paper. If 20 of those
squares sit inside a table's outline, the **overlap ratio** is 20%. The default
requires at least 15%. For a person overlapping multiple tables, only the table
with the greatest overlap gets that person; an exact tie uses the first saved
table. This prevents counting one person at multiple tables, but perspective
and overlapping zones can still produce incorrect assignments.

The code fills the actual polygon, including concave shapes, rather than using
a rectangle around the zone. It refuses a video whose resolution differs from
the saved map, so coordinates cannot silently shift. It cannot detect a camera
angle change at the same resolution; that still requires remapping.

YOLO is run on a smaller image internally to save computation, but returns boxes
in original video coordinates. The display is also resized only after matching.


`CAMERA_SOURCE` is also supported, as explained in the RTSP section. Diagnostic
output paths are replaced if they already exist; choose a new name to keep old
results. The report contains processed-frame counts, peak people in one image,
per-table matched-frame totals, and the final detections. It is not historical
occupancy analytics or a count of unique visitors.

The default uses the CPU for compatibility. `--device mps` requests the Apple
GPU if your installed PyTorch supports it. `--confidence 0.25` admits less-certain
detections and can increase both detections and false positives.

YOLO looks at a resized copy of each image; `--image-size` sets its longest side.
The default is **960**. On the sample video, the original 640 default missed the
diner at Table 3 in most frames (matched in 24 of 240 frames), so that table stayed
green although he sat there the whole clip. At 960 he was matched in all 240 frames,
and people at the back tables were found more often. The cost is speed: in a CPU
test, 960 processed about half as many frames per second as 640. If playback is too
slow for your machine, use `--image-size 640` or try `--device mps`.

### Limits and troubleshooting

- A server, busser, customer or passerby can all produce a match. This phase does
  not classify staff, confirm seating, smooth missed detections, start timers,
  detect cleaning, or send alerts. Those decisions belong to Phase 3.
- A tabletop-only zone can miss seated people whose boxes lie mostly outside it.
  If cyan boxes look correct but the table remains green, redraw around the
  chairs or cautiously lower `--overlap`. Avoid including aisles and neighboring
  tables. A small overlap threshold can wrongly count a passerby.
- Detections can flicker when people are partly hidden or very small. We must
  not interpret a single missed image as someone leaving in Phase 3.
- Video files process every frame. If inference is slower than the video's
  frame rate, playback slows down. This prototype does not guarantee real-time
  speed or low-latency RTSP buffering. A dropped camera connection stops with an
  error instead of treating tables as empty; reconnect and restart manually.
- A first-run download error means the model weights could not be obtained.
  Check Internet access and rerun. Later runs reuse `models/yolo26n.pt` offline.
- `Video size differs from the saved map` means the image dimensions changed.
  Use the original source settings or create a matching map; don't hand-edit
  the recorded dimensions to hide the mismatch.
- Your current sample video is 10 seconds (240 frames at 24 fps). It can test
  detection but does not establish performance over a full table lifecycle.

We added the code that finds people and connects them to table zones. You learn
the distinction between a detection, a tracked ID, and a confirmed table state.
The next step is to inspect the preview and see where the matches are right or
wrong before adding timers and states.

## Phase 3: table memory, timers, alerts and API

The detector is like a pair of eyes. Phase 3 adds a notebook: it remembers what
happened to each table and decides when a change has lasted long enough to count.
The technical name for these rules is a **state machine**.

The new code is already in these locations:

```text
backend/
  api.py                 # FastAPI addresses and request validation
  state.py               # Lifecycle rules and SQLite storage
scripts/
  state_client.py        # Sends detection observations to the API
  detect_people.py       # Now supports --api and state-colored previews
tests/
  test_state_api.py      # Lifecycle, timing, persistence and API checks
data/
  restaurant.sqlite3     # Created by the server; contains runs and events
```

`api.py` provides an **API**: a set of addresses other programs can use to read
or update information. `state.py` stores the notebook in **SQLite**, a database
contained in a local file. `state_client.py` sends only table matches and temporary
person IDs; it does not upload video images. These separate pieces let the future
dashboard refresh without creating extra detectors.

### What changes a table's state?

| From | Evidence | To |
| --- | --- | --- |
| Free (green) | Unlabeled people remain matched for at least 2 seconds | Occupied (red) |
| Occupied (red) | No customer matches for at least 3 seconds | Needs cleaning (yellow), with a console alert |
| Needs cleaning (yellow) | A manually identified staff track newly enters, with no customers present | Free (green), using staff entry as a cleaning proxy |
| Needs cleaning (yellow) | Staff explicitly confirm cleaning through the API, with no observed customers | Free (green) |
| Needs cleaning (yellow) | A new customer presence lasts at least 2 seconds | Occupied (red), starting a new visit |

The short confirmation delays are called **debouncing**. They reduce flicker from
missed detections, but a passerby who overlaps a zone long enough can still trigger
occupancy. A lost camera connection is not interpreted as everyone leaving.
An observation gap longer than five seconds clears pending arrival/departure
evidence. Historical events and the last known table states are retained.

An ungreeted alert fires once per visit after its deadline. A recorded greeting
suppresses that alert. A cleaning alert fires once when the table enters yellow.
Alerts are printed to the API terminal and stored as database events. There is
no phone notification or webhook delivery yet. Console delivery is best effort;
the database is the saved alert history.

### Staff interactions are explicit

All unclassified detections are treated as possible customers. YOLO does not
know a person's job. There are two supported ways to record staff activity:

- Mark an occupied table greeted, or a yellow table cleaned, through the API.
  This is a human confirmation and does not require identifying a particular person.
- While a run is actively receiving observations, mark a visible tracking ID
  (for example `P7`, entered as `7`) as staff. Starting with the next observation,
  that ID is excluded from customer counts. Its presence at an occupied table
  records a greeting; a new entry into an empty yellow zone acts as a cleaning signal.

Staff labels belong only to the current run and are cleared on replay. Tracker
IDs can change or switch between people; inspect labels and remove incorrect ones.
Uniform-color recognition is not implemented. Neither presence nor staff entry
proves a real greeting or cleaning task happened; these are prototype assumptions.
A staff member who was already present while customers left does not automatically
clean the table: a new entry or explicit confirmation is required.

In `/docs`, expand an endpoint, choose **Try it out**, fill its fields, then choose
**Execute**. Copy the current `source.id` from `GET /api/tables` into `run_id` when
performing a staff action. For example, the body for greeting a table is:

```json
{"run_id": "COPY-THE-CURRENT-SOURCE-ID-HERE"}
```

Use `POST /api/tables/table_1/greet` with that body to record a greeting. A cleaning
confirmation uses `POST /api/tables/table_1/clean`. A completed video's last state
may still receive manual confirmations; its media timer remains frozen, while the
event's real UTC recording timestamp records when you made the confirmation.

### API reference

| Method and address | Purpose |
| --- | --- |
| `GET /health` | Check whether the API is running |
| `GET /api/tables` | Current states, colors, timers, observed counts, map and source health |
| `GET /api/events` | Persistent chronological event history |
| `GET /api/alerts` | Persistent greeting and cleaning alerts |
| `POST /api/tables/{table_id}/greet` | Confirm a greeting; body contains `run_id` |
| `POST /api/tables/{table_id}/clean` | Confirm cleaning; body contains `run_id` |
| `POST /api/staff/{track_id}` | Mark a currently visible ID as staff; body contains `run_id` |
| `DELETE /api/staff/{track_id}` | Remove a staff label; body contains `run_id` |
| `POST /api/runs` | Start a run; normally called by the detector |
| `POST /api/runs/{run_id}/observations` | Submit matched people; normally called by the detector |
| `POST /api/runs/{run_id}/stop` | Finish a run; normally called by the detector |
| `GET /api/waitlist` | Parties waiting or texted, plus the ntfy topic |
| `POST /api/waitlist` | Add a party: `name`, `party_size`, optional personal `topic` |
| `POST /api/waitlist/{id}/notify` | Text the party that a table is ready; body contains `table_id` |
| `POST /api/waitlist/{id}/close` | Mark the party `seated` or `removed` |

`GET /api/events` and `/api/alerts` accept `run_id`, `after_id`, and `limit` query
parameters. They return oldest-first, up to 100 records by default; use the last
returned event ID as `after_id` to fetch the next page. Maximum page size is 1000.
Every state-change record includes the old state, new state, reason, run ID,
table ID, UTC `recorded_at` timestamp, and `source_seconds`. The latter is video
time for replays, so it must not be mistaken for real restaurant operating hours.
Completed occupied periods include their measured duration for later analytics.

The API rejects invalid requests, duplicate/out-of-order frames, unknown tables,
and a second simultaneous detector run. Each new replay starts a separate set of
table states, preserving earlier events. An API restart retains the last states
and marks the old source interrupted. After restarting the API, restart the
detector as well; old run IDs cannot resume observation submission.

### How the dashboard must interpret these results

`source.fresh` becomes false when observations are more than five seconds old,
or the source stops. `available` is false for stale sources, unobserved tables,
and tables with a pending arrival. Initial green is only an assumption until a
first observation arrives. The Phase 4 dashboard shows source health alongside
state colors, rather than presenting the last known green state as current truth.

The API does not store faces, video or images. It stores temporary IDs in the
current run snapshot and inferred table events. Automatic occupancy is still only
as accurate as the detector and polygons. The dashboard is Phase 4; historical
peak-hour reports are not built yet, but this phase stores the event history they need.

### Troubleshooting and verification

- **State API request failed:** the detector cannot reach the server, or the
  server rejected the action. Start the API first and check the printed detail.
- **A detector run is already active:** stop the other detector with `q` or
  Ctrl+C. If it crashed, copy the current run ID from `/api/tables` and use the
  stop endpoint in `/docs` with `{"reason":"stopped"}` before restarting.
- **Detector and API use different table maps:** restart the API using the
  matching map. `RESTAURANT_ZONES` sets its map path; the detector uses `--zones`.
- **Cleaning requires a needs-cleaning table:** the state or observed customer
  count doesn't permit cleaning. Check the detector preview and table state.
- **No five-minute alert in the sample:** the clip lasts only ten seconds. Use
  `--greet-after 5` for a demonstration, or a longer recording for the real deadline.

`RESTAURANT_DB` can select another SQLite file, for example to keep experiments
separate. It must be set before starting the API. Stop the server with Ctrl+C.
Keep the `.sqlite3`, `-wal` and `-shm` files together while it is running; don't
delete them to reset a replay. Starting a new run is the supported way to replay.

Run the automated checks with:

```bash
python -m unittest discover -s tests -v
```

## Phase 4: the host-stand dashboard

The dashboard is a web page for whoever runs the host stand. It reads everything
from the Phase 3 API every two seconds; it never opens the camera or the database
itself, so refreshing it cannot start a second detector.

### Run it

Start the API first (Phase 3), then in another activated terminal:

```bash
streamlit run dashboard/app.py
```

Open <http://127.0.0.1:8501>. `.streamlit/config.toml` keeps the page on this
computer only and turns off Streamlit's usage statistics. Start the detector with
`--api http://127.0.0.1:8000` in a third terminal to see live states.

| Setting | Default | Purpose |
| --- | --- | --- |
| `RESTAURANT_API_URL` | `http://127.0.0.1:8000` | Where the dashboard finds the API |
| `RESTAURANT_TIMEZONE` | `America/New_York` | Time zone for the activity log |

### Look and motion

The dashboard uses a dark "after hours" theme (set in `.streamlit/config.toml`):
warm espresso panels, linen text, and one color per table state — sage for free,
claret for occupied, saffron for needs cleaning. The Archivo typeface is bundled in
`dashboard/static/fonts/` (SIL Open Font License, `OFL.txt`), so nothing is
downloaded from the internet.

### The animated floor plan

The centerpiece is a top-down view of the dining room (`dashboard/floor_plan/`):
wood floor, the bar along the top wall, the entrance and kitchen doors, and every
mapped table with its chairs, plates and a candle. Tables keep their left/right and
front/back positions from your camera map; far tables are spread out to undo the
camera's perspective, and each table gets 2, 4 or 6 seats from its corrected size.

People on the plan come only from the detector, never from decoration:

- **Guests** sit at a table for each customer the camera matched to it (up to the
  seat count). When a table fills, guests walk in from the entrance and sit down;
  when it empties, they walk out. A guest is removed only after two refreshes in a
  row agree, so a single missed detection doesn't make someone vanish.
- **Arriving** guests (a detection that hasn't lasted long enough to count as
  seated) wait standing beside the table.
- **Servers** (white shirt, tray) appear only for tracks you've marked as staff, and
  walk out from the kitchen.

Other motion shows state: occupied tables get food on the plates, a flickering
candle and the odd conversation bubble; tables needing attention send out a pulsing
ring with a red "Greet" or amber "Clean" label that bounces; a dirty table shows
crumbs and sparkles, then a small burst when it's cleaned; the selected table gets a
moving dashed outline. Hover over a table for its details, and click it (or select
it with Tab and press Enter) to open it in **Table details**. When the data isn't
live, the room dims and idle motion stops, so frozen states never look current.

Around the plan: a slow ambient glow behind the page, frosted-glass panels, the
title rising in once when the page opens, pop-up notifications for new alerts (old
alerts are never replayed), and a glow on the "Needs attention" count.

If your computer's "reduce motion" accessibility setting is on, all animation is
turned off and people move straight to their places.

### Waitlist: text guests when their table is ready

When the room is full, add a party (name and size) in the **Waitlist** panel. When
a table is free, the panel says which table is ready and who's next. Pick the
table (tables that fit the party are listed first) and tap **Text guest**. The
guest's phone gets a push notification:

> **Table 3 is ready** — Hi Akash, table 3 is ready for your party of 2. Please come to the host stand and we'll seat you.

The table then shows **Held** on the floor plan until you tap **Seated** (or
**Remove**). The host always taps the button: a detection mistake never sends a
message by itself. You can't text for a table that's occupied or already held for
someone else, and if sending fails, the party stays on the waitlist with an
explanation.

Messages go through [ntfy](https://ntfy.sh), a free push-notification service, so
there's no account or phone-number setup:

1. Install the free **ntfy** app on your phone (App Store or Google Play).
2. On the dashboard, open **Get these messages on your phone** in the Waitlist panel
   and copy the topic name (it looks like `dineassist-5e6423b40f`).
3. In the app, tap **+** and subscribe to that topic. Leave the server as `ntfy.sh`.

The topic is created once and saved in the database. Anyone who knows a topic name
can read its messages, and the guest's name is in the message, so keep the topic
private and use a fresh one for a public demo. This computer needs internet access
to send. Settings for the API (set before starting it):

| Setting | Default | Purpose |
| --- | --- | --- |
| `RESTAURANT_NTFY_TOPIC` | random, saved in the database | Topic every message goes to |
| `RESTAURANT_NTFY_SERVER` | `https://ntfy.sh` | Use your own ntfy server instead |

### What's on the page

- **Status bar:** whether the source is live, a finished replay, delayed or offline.
- **Counts:** available, occupied, needs cleaning and needs attention. "Available
  now" shows "—" whenever the data is not fresh, because a stale green table may
  no longer be free.
- **Floor map:** the animated floor plan described above. Grey means not yet
  observed. Click a table to inspect it. Use **Show** to dim every table outside
  one group, such as "Needs attention".
- **Table details:** time seated or time in state, a bar counting down to the
  greeting deadline, and the **Record greeting** and **Confirm cleaned** buttons. Buttons are disabled when the
  action isn't allowed (for example, cleaning a table that still has customers).
- **Identify staff:** mark a visible P-number as staff for this run. Do this for
  servers early in a run: until labeled, a server counts as a possible customer,
  and their visits do not count as greetings. In the saved sample run (with
  `--greet-after 5`) no one was labeled, so five of the six occupied tables raised
  an "ungreeted" alert; the sixth was seated too late to reach the deadline.
- **Service queue and All tables:** tables needing attention first, plus a sortable list.
- **Activity log:** recent events from the current run, filterable, with CSV export.
  Exported cells starting with `=`, `+`, `-` or `@` are prefixed with `'` so
  spreadsheet programs don't run them as formulas.

If the API stops, the page keeps the last data it received, marks it as cached,
and disables actions until the connection returns.

### Troubleshooting

- **"Cannot reach the restaurant service":** the API isn't running or uses a
  different address. Start it, or set `RESTAURANT_API_URL`.
- **"Waiting for video":** the API is up but no detector run has started.
- **Buttons are greyed out:** the source is stale or offline, or the table's state
  doesn't allow that action.
- **Port 8501 already in use:** another Streamlit app is running; stop it, or run
  `streamlit run dashboard/app.py --server.port 8502`.
